# Scientific evaluator proposal review

`evaluator-proposal-contract.json` is the machine-readable proposal schema. `qn_atlas.evaluator_review.validate_proposal` performs additional cross-field checks and returns missing evidence. Neither operation imports, evaluates, installs, or runs submitted code. An implementation SHA256 identifies reviewed bytes; the isolated runner must independently recompute it before execution. This module does not implement that runner.

The descriptor retains the evaluator registry's `axis_id`, `axis_version`, `implementation_id`, `implementation_version`, `name`, `dependencies`, `output_kind`, and `projections`. A scientific proposal additionally states supported scopes and evidence levels, physical units, versioned projection specifications, and an execution contract. Each projection names its formula, output type, units and missing-value policy. Dependencies name required nodes; a dependency name alone does not prove availability or mathematical validity. The execution contract specifies input/output schemas, failure behavior, resources, determinism, the implementation hash and `isolated_reviewed_runner` mode.

Every proposal must include a mathematical definition, scope boundaries, failure/counterconditions, checkable primary sources or explicit proof artifacts, and three reproducible examples:

- A positive example with an independently derived expected result.
- A counterexample showing an excluded overclaim or a failure of the asserted property outside its conditions.
- A degenerate example, such as zero vector field, constant trajectory, singular input, missing dependency, or zero normalization scale, with an explicit expected failure/status/value policy.

Each expectation records status, scope, evidence level, assertion relation, oracle, derivation, and the overclaim it excludes. Equality and interval/tolerance checks need an expected value; tolerance assertions need a finite nonnegative absolute tolerance. An unknown/unsupported result must not use zero as a substitute value. Numerical samples may be `estimated` at sample/trajectory/algorithm scope; they cannot establish an equation-wide or domain-wide theorem. This conservative rule does not prohibit a separately justified interval certificate.

For example, the scalar local-derivative evaluator on `x'=a*x` should return the analytically derived derivative `a`: use `a=-1` as a decay example, `a=1` as the counterexample to decay, and `a=0` as the degenerate case. All three have an equilibrium trajectory from zero, illustrating why that trajectory alone cannot identify the derivative or stability. These formulas are elementary proof artifacts; tests in `test_evaluator_review.py` use them to validate the workflow, not to certify arbitrary submitted mathematics.

Independent **Astra** mathematical review is mandatory. A usable external review record includes the exact proposal SHA256, authenticated reviewer identity distinct from the author, `reviewer_model='gpt-6-astra'`, an accepted decision, actual review artifact SHA256, a review record identifier, mathematical findings, and explicit checks of independence, expectations, scope and sources. The model name inside a JSON record cannot authenticate its author: the caller must supply records from its own authenticated review store. Embedded proposal approval flags or model names have no effect.

Each executed example likewise needs an external test record bound to the proposal hash, example ID and example hash, with outcome, actual artifact SHA256 and runner record ID. This validator checks those bindings, not artifact contents or runner honesty. Never synthesize a passing record because the proposed expectation looks plausible. Never execute untrusted evaluator code on the host to obtain a record. A separate reviewed isolated runner and an independent mathematical reviewer remain responsible for actual execution and assessment.

Return states are `invalid`, `needs_evidence`, and `ready_for_governed_execution`. Even the final state has `scientific_certification=false` and `executed_code=false`: it means that the authenticated caller supplied the required review/test records, not that this data validator has proved mathematical truth. Any change to the proposal invalidates old hash bindings. The deployment/registry owner must also check the implementation hash, allowed dependency graph, output contract, execution isolation and current version at execution time.

`review_builtin_descriptors` inventories existing descriptors without evaluating their axes. A bootstrap descriptor that omits the extended scientific fields is reported as incomplete, not retrospectively certified or silently rejected from the existing registry. Review results should be stored alongside actual file hashes and explicit limitations. Read-only source review, algebraic checks, and executed tests must be recorded separately.
